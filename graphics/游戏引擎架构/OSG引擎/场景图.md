# 核心

场景图的本质 ”。层级 = 状态继承 + 空间组织 + 遍历控制

是用层级来控制：

- State 继承:**最终使用的 StateSet = 遍历路径上所有 StateSet 叠加后的结果,子节点的 StateSet 会覆盖父节点中相同类型的 StateAttribute**
- RenderBin
- Cull 结构
- Update 分离
- Pass 分类

# 基础场景结构

建议采用**“功能分层式结构”**，而不是随便 addChild。

```
Root
 ├── StaticGroup
 │    ├── OpaqueGroup
 │    └── TransparentGroup
 │
 ├── DynamicGroup
 │    ├── OpaqueDynamic
 │    └── TransparentDynamic
 │
 ├── OverlayGroup
 │
 └── DebugGroup
```

### 为什么这样好？

- 透明与不透明物体天然隔离
- 静态和动态物体可分开优化
- 后期加延迟渲染、OIT、RTT 都不会乱
- Cull traversal 更清晰

这是第一条大原则：

> 按“渲染特性”分层，而不是按“业务逻辑”分层。



# StateSet 继承的实战策略

##### 尽量把状态放在“Group 层”，统一挂shader,不在叶子节点反复覆盖State

例如：

```
transparentGroup->getOrCreateStateSet()
    ->setRenderingHint(osg::StateSet::TRANSPARENT_BIN);
```

而不是每个子节点都设。

原因：

- **减少 State 切换**
- **保证继承一致**
- **易维护**

### 核心经验

> StateSet 应该尽量往上提，而不是往下分散。

# 不要滥用 Transform

很多人每个物体都套一层 MatrixTransform。

这会导致：

- Cull 深度增加
- 更新 traversal 变慢
- 结构臃肿

经验：

- **静态模型不要包 transform**
- **只有需要变换时才加**
- **多物体共用 transform**



# 按“Pass”分组（高级玩法）

如果做延迟渲染，建议**场景图结构直接反映 Pass**。

例如：

```
Root
 ├── GBufferGroup
 ├── ShadowCasterGroup
 ├── TransparentPassGroup
 └── LightingPassGroup
```

这样：

- 不需要 runtime 动态筛选
- 不需要每帧遍历过滤
- 结构清晰

# 节点职责单一原则（非常重要）

**一个 Group 不要承担多种职责。**

错误例子：

```
GroupA
 ├── 既有透明
 ├── 又有不透明
 ├── 还挂 shader
 ├── 还负责 update callback
```

后期你根本不知道问题在哪。

建议：

- 渲染分类一个层级
- 状态控制一个层级
- 动态更新一个层级

# 性能相关结构经验

#### 1.大量静态物体

使用：

- Static Group
- 关闭动态更新
- 合并 geometry

#### 2.小物体很多

考虑：

- Instancing
- Geometry 合批
- 不要一个物体一个 geode
