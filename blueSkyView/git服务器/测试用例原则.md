------

# 一、先建立一个核心原则（非常重要）

## ✔ 好的测试用例 = “场景描述”，不是“代码覆盖”

很多人写测试失败的根源是：

> 把测试写成“函数执行记录器”，而不是“行为验证器”

------

## ✔ 一个正确测试用例应该回答三件事：

```text
1. 输入是什么？
2. 系统做了什么行为？
3. 最终状态是否符合预期？
```

------

# 二、单元测试（Unit Test）最佳实践

------

# 1. 单元测试写法核心模型（推荐）

## ✔ AAA 模型（工业标准）

```text
Arrange（准备）
Act（执行）
Assert（验证）
```

------

## 示例（图形/状态机）

```cpp
TEST(Player, JumpState)
{
    // Arrange
    Player p;
    Input input;
    input.pressJump();

    // Act
    p.update(input);

    // Assert
    ASSERT_TRUE(p.isJumping());
}
```

------

# 2. 单元测试设计原则

------

## ✔ 原则1：只测一个行为（Single Behavior）

❌ 错误：

```cpp
TEST(Player, AllActions)
```

✔ 正确：

- Jump
- Walk
- Attack

拆开测

------

## ✔ 原则2：不要测实现细节

❌ 错误：

```cpp
EXPECT_CALL(renderer, drawCallCount == 3);
```

✔ 正确：

```cpp
EXPECT_TRUE(scene.containsMesh("Cube"));
```

------

## ✔ 原则3：输入尽量“最小化”

不要构造复杂系统依赖：

```text
坏测试 = 10个对象 + 5个mock + 3层依赖
```

------

## ✔ 原则4：测试“状态变化”，不是“函数调用”

✔ 推荐：

```cpp
ASSERT_EQ(state, State::Running);
```

------

# 三、集成测试（Integration Test）最佳实践

------

# 1. 集成测试写法模型

## ✔ “场景驱动模型”（推荐）

```text
Given（系统状态）
When（多个模块协作）
Then（系统结果）
```

------

## 示例（渲染引擎）

```cpp
TEST(RenderIntegration, ShadowPipeline)
{
    // Given
    Engine engine;
    Scene scene;
    scene.addLight();
    scene.addCube();

    engine.setScene(scene);

    // When
    Image img = engine.renderFrame();

    // Then
    ASSERT_GT(meanBrightness(img), 0.2);
}
```

------

# 2. 集成测试最佳实践

------

## ✔ 原则1：不要 mock 核心链路

❌ 错误：

- mock renderer
- mock scene
- mock material

👉 结果：测不到系统问题

------

## ✔ 原则2：允许使用“fake dependency”，但不能fake业务

✔ 可以 fake：

- network
- file IO
- GPU backend（mock driver）

------

## ✔ 原则3：测试“系统协作结果”

不要测：

- 某个函数调用

要测：

- 整个pipeline是否正确

------

## ✔ 原则4：输入必须是“场景级别”

例如：

```text
scene.json
mission.xml
flight_plan.dat
```

------

# 四、端到端测试（E2E）最佳实践

------

# 1. E2E测试模型

## ✔ “用户行为驱动模型”

```text
Start system
→ simulate user input
→ run full pipeline
→ validate final output
```

------

## 示例（飞行模拟器）

```cpp
TEST(E2E, FlightMission)
{
    Engine engine;
    engine.loadMission("mission.xml");

    SimulatePilotInput(engine);

    engine.runForSeconds(300);

    ASSERT_LT(StateDrift(engine), 0.01);
}
```

------

# 2. E2E最佳实践

------

## ✔ 原则1：少而精（10~50个足够）

不要写太多，否则：

- 慢
- 不稳定
- CI炸

------

## ✔ 原则2：用“黄金结果”而不是细节

✔ 推荐：

- image compare
- state snapshot diff
- trajectory compare

------

## ✔ 原则3：允许一定误差（epsilon）

```cpp
ASSERT_NEAR(value, expected, 0.01);
```

------

# 五、测试用例设计“黄金模板”（非常实用）

------

## ✔ 通用模板（强烈推荐统一）

```text
TEST(Name, Scenario)
{
    // 1. Arrange（构造最小世界）
    
    // 2. Act（触发行为）
    
    // 3. Assert（验证结果）
}
```

------

# 六、测试用例质量检查清单（重点）

写完后问自己：

------

## ✔ 是否只测一个行为？

------

## ✔ 是否可以不用看实现就能理解？

------

## ✔ 是否稳定（无随机依赖）？

------

## ✔ 是否能快速定位bug？

------

## ✔ 如果失败，是不是“明确原因”？

------

# 七、常见坏测试（非常重要）

------

## ❌ 坏1：测试实现细节

```cpp
EXPECT_EQ(vector.size(), 3);
```

问题：重构就废

------

## ❌ 坏2：过度mock

👉 测不到真实逻辑

------

## ❌ 坏3：测试太大（集成混成E2E）

👉 不可维护

------

## ❌ 坏4：没有断言“结果”，只断言“过程”

------
