下面按"整体架构 → 关键设计点 → 落地示例"的顺序展开，尽量给出可以直接落地的方案，而不是抽象讨论。

---
  一、整体架构

  推荐一个单可执行文件 + Catch2 内自校验的架构：

  rendering exe（Catch2）
     ├─ 每个 TEST_CASE:
     │    1) 起引擎 → 加场景 → 配相机 → 离屏渲染 → 写 PNG
     │    2) 调 ImageMagick compare 或调用自带库对比 golden
     │    3) REQUIRE(metric < 阈值)
     └─ 通过 catch_discover_tests 拆成 N 个 CTest 用例

  为什么不把"渲染"和"对比"拆成两个 CTest 用例：拆开后一次失败只知道"某张图不对"，看不到相机参数、场景、渲染耗时等上下文；合并到 Catch2 里，INFO/CAPTURE
  可以把这些都打出来，失败信息自然完整，也天然可用 catch_discover_tests 拆多用例。

---
  二、目录结构

  engine/rendering_test/
  ├── CMakeLists.txt
  ├── framework/                    # 复用代码，不含 TEST_CASE
  │   ├── HeadlessRenderer.h/.cpp   # 参考 vsgheadless.cpp 抽出的封装
  │   ├── ImageCompare.h/.cpp       # 对 ImageMagick 的封装
  │   └── TestScene.h/.cpp          # 场景/相机的 helper
  ├── cases/                        # 每个 cpp 一组相关用例
  │   ├── geometry_cases.cpp
  │   ├── material_cases.cpp
  │   └── lighting_cases.cpp
  ├── scenes/                       # 测试用小场景（*.vsgt）
  ├── golden/                       # 参考图（走 Git LFS）
  │   └── <gpu-tag>/                # 可选：按 GPU/驱动分桶
  └── main.cpp                      # Catch2 main + 自定义 CLI

  要点：
  - scenes/ 只放为测试专门做的最小场景，不要用生产资产（体积大、变化频繁，会污染 golden）。
  - golden/ 用 Git LFS，PNG 二进制不适合走普通 git。
  - 输出目录（actual、diff）放 build 目录下，.gitignore 掉。

  三、离屏渲染封装

  从 vsgheadless.cpp 抽一个可编程接口，测试用例调它就行：

  struct RenderRequest {
      std::filesystem::path scenePath;
      VkExtent2D extent{1024, 1024};
      vsg::dvec3 eye, center, up;
      double fovY = 30.0;
      double nearFarRatio = 0.001;
      uint32_t seed = 0;             // 若引擎里有随机成分（噪声、抖动）
      uint32_t frameCount = 1;       // 需要跑动画/时序稳态时 > 1
  };

  struct RenderResult {
      std::filesystem::path colorPng;
      std::filesystem::path depthPng;  // 可选
      double gpuTimeMs = 0;
  };

  RenderResult render(const RenderRequest&);

  几个必须的细节：
  1. 每个用例独立设备还是共享设备？——推荐共享 vsg::Instance/Device（单例 fixture），只重建 view/framebuffer。省几百毫秒/用例。
  2. 强制 deviceIndex：CI 上如果有多 GPU（比如集成 + 独立），要能通过环境变量 ZEUS_TEST_GPU_INDEX 指定，否则 golden 会随机漂。
  3. 关闭一切非确定性：TAA、异步计算、时间相关动画（可以固定 simTime = 0.0）、纹理流式加载（强制同步等 IO 完）。这一步不做的话 golden 永远稳不下来。
  4. 等 GPU 完成再写盘：waitIdle + vkQueueWaitIdle，否则拿到未完成图。

  四、图像对比策略（重点）

  不要只用一种指标。分层判定：

  ┌──────────┬─────────────────────────────┬────────────────────┐
  │   层级   │            指标             │      触发含义      │
  ├──────────┼─────────────────────────────┼────────────────────┤
  │ 快速判定 │ AE（不同像素数） + -fuzz N% │ 完全一致或差异极小 │
  ├──────────┼─────────────────────────────┼────────────────────┤
  │ 主判定   │ SSIM 或 PSNR                │ 抗抖动，人眼可接受 │
  ├──────────┼─────────────────────────────┼────────────────────┤
  │ 兜底     │ MAE（平均绝对误差）         │ 排除大范围 shift   │
  └──────────┴─────────────────────────────┴────────────────────┘

  命令行示例（ImageMagick 7 用 magick 前缀）：

  magick compare -metric AE  -fuzz 1% golden.png actual.png diff_ae.png
  magick compare -metric PSNR              golden.png actual.png diff_psnr.png

  - AE + -fuzz 1%：AA 边缘、量化噪声允许 1% 内视为一致。
  - PSNR：> 40 dB 通常肉眼不可辨，可以以 40 或 45 为线。
  - 退出码：0 = 完全一致，1 = 有差异（不是错误），2 = 命令错误。测试逻辑不要用退出码判定，要解析 stderr 里的数值。

  封装建议：

  struct CompareMetrics {
      double ae = 0;           // 差异像素数
      double aePercent = 0;    // 差异像素占比
      double psnr = 0;         // dB
      std::filesystem::path diffImage;
  };
  CompareMetrics compareImages(const std::filesystem::path& golden,
                               const std::filesystem::path& actual,
                               double fuzzPercent = 1.0);

  用 popen/_popen 起进程读 stderr 拿数值；不要把 ImageMagick 当 C 库链接（编译依赖太重）。

  在测试里：

  TEST_CASE("Textured cube renders identically", "[render][basic]") {
      auto res = render({.scenePath = scenes()/"cube.vsgt",
                         .extent = {512, 512},
                         .eye = {3, 3, 3}, .center = {0,0,0}, .up = {0,0,1}});

      auto m = compareImages(golden()/"cube.png", res.colorPng, /*fuzz*/1.0);
    
      INFO("actual  = " << res.colorPng);
      INFO("diff    = " << m.diffImage);
      CAPTURE(m.aePercent, m.psnr);
    
      REQUIRE(m.aePercent < 0.1);   // 差异像素 < 0.1%
      REQUIRE(m.psnr      > 40.0);  // 或 SSIM > 0.995
  }

  五、Golden 的更新与失败取证

  更新模式：给 exe 加一个 --update-golden 参数（Catch2 支持自定义 CLI）。开启后不比较，只把 actual 覆盖到 golden。开发者本地跑：

  RenderingTest "[render][basic]" --update-golden
  git lfs track "engine/rendering_test/golden/**"
  git add ... && git commit

  失败取证（CI 必备）：
  - 失败时把 actual.png + diff.png 拷到一个已知目录（如 build/rendering_test_artifacts/）。
  - CI 里把该目录整个上传成 artifact，PR 里能直接下载看图。
  - Catch2 里用 INFO() 打路径就够了，不要写复杂 reporter。

  六、CTest 注册（用 catch_discover_tests）

  比单个 add_test 强得多——每个 TEST_CASE 都是独立 CTest 用例，能 -R 过滤、并行、单独重跑失败项：

  set(TARGET_NAME RenderingTest)
  add_executable(${TARGET_NAME} ...)
  target_link_libraries(${TARGET_NAME} PRIVATE Catch2::Catch2WithMain ZeusRuntime vsg::vsg)

  # 让 exe 能找到 dll（前一个问题里的坑）
  add_custom_command(TARGET ${TARGET_NAME} POST_BUILD
      COMMAND ${CMAKE_COMMAND} -E copy_if_different
              $<TARGET_RUNTIME_DLLS:${TARGET_NAME}> $<TARGET_FILE_DIR:${TARGET_NAME}>
      COMMAND_EXPAND_LISTS)

  # 找 ImageMagick，缺失时给友好提示
  find_program(MAGICK_EXECUTABLE NAMES magick REQUIRED)

  # 把路径以宏形式喂给测试代码，避免运行时靠 CWD 找资源
  target_compile_definitions(${TARGET_NAME} PRIVATE
      ZEUS_TEST_SCENES_DIR="${CMAKE_CURRENT_SOURCE_DIR}/scenes"
      ZEUS_TEST_GOLDEN_DIR="${CMAKE_CURRENT_SOURCE_DIR}/golden"
      ZEUS_TEST_OUTPUT_DIR="${CMAKE_CURRENT_BINARY_DIR}/output"
      ZEUS_MAGICK_EXECUTABLE="${MAGICK_EXECUTABLE}")

  include(Catch)
  catch_discover_tests(${TARGET_NAME}
      EXTRA_ARGS -s --verbosity high
      PROPERTIES
          LABELS "rendering;regression"
          TIMEOUT 60
          RUN_SERIAL TRUE)   # 共享 GPU，先串行；稳了再放并行

  之后：

  ctest -C Debug -L rendering --output-on-failure -j 1
  ctest -C Debug -R "Textured.*cube"                # 只跑某组
  ctest -C Debug --rerun-failed                     # 只跑上次失败

  七、确定性与 CI 的现实问题（最容易踩坑）

  这一部分很多团队做完发现 golden 三天两头飘，最后放弃回归测试——必须提前想清楚：

  1. 同一张 golden 跨 GPU 厂商基本不可能通过（NV/AMD/Intel 的浮点/纹理过滤实现有细微差别）。

    - 方案 A（推荐）：CI 用 Mesa lavapipe（Vulkan 软光栅），跨机器 bit-identical。本地开发不强制，只要求本地跑通即可，CI 是唯一 golden 判据。
    - 方案 B：golden/<vendor>/ 分桶，用 VK_LAYER_MESA_device_select 或 vendor id 选目录。维护成本高，不推荐。
  2. 驱动升级也会改结果。CI 用固定版本的 lavapipe（docker image 里锁死）；本地开发者升驱动无所谓，反正判据是 CI。

  七、确定性与 CI 的现实问题（最容易踩坑）

  这一部分很多团队做完发现 golden 三天两头飘，最后放弃回归测试——必须提前想清楚：

  1. 同一张 golden 跨 GPU 厂商基本不可能通过（NV/AMD/Intel 的浮点/纹理过滤实现有细微差别）。

    - 方案 A（推荐）：CI 用 Mesa lavapipe（Vulkan 软光栅），跨机器 bit-identical。本地开发不强制，只要求本地跑通即可，CI 是唯一 golden 判据。
    - 方案 B：golden/<vendor>/ 分桶，用 VK_LAYER_MESA_device_select 或 vendor id 选目录。维护成本高，不推荐。

  3. PR 里出现 golden 变更要走 code review：LFS 里的 PNG 变更 diff 不好看，规定"改 golden 必须在 PR 描述里说明原因 + 附对比截图"。
  4. 不要一开始就写太多用例。5-10 个精挑细选的场景（几何、材质、透明、阴影、后期），每个 512×512，跑起来快、维护得动。等框架稳了再扩。

---
  八、渐进式落地建议

  按这个顺序做，中间任一步都能停下来交付：

  1. HeadlessRenderer + 1 个 hardcode 的用例（cube），本地能出 PNG。
  2. ImageCompare 用 ImageMagick 打通，本地手动比。
  3. Catch2 里写死一条断言，catch_discover_tests 注册到 CTest。
  4. 加 --update-golden CLI。
  5. CI 换 lavapipe，把 golden 提交进 LFS。
  6. 加失败 artifact 上传。
  7. 铺 10 个左右场景，形成用例集。
