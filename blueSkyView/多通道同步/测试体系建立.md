**有必要。** 多通道同步是飞行模拟器里典型的“隐蔽失败”模块：时钟漂移、CIGI 状态不一致、Present 时机错位，往往在真实多 GPU / 多进程环境才暴露，靠手工联调成本高且难回归。建议以**单元测试为主、集成测试为辅**，再保留少量多机/多卡手工或脚本化验收。

仓库里已有 Catch2 单元测试和渲染对比测试基础设施，新模块可直接挂上去。

| 层级          | 是否需要     | 作用                                                         |
| ------------- | ------------ | ------------------------------------------------------------ |
| 单元测试      | **强烈建议** | 测时钟、协议编解码、同步状态机、调度决策，可 CI、可确定性复现 |
| 集成测试      | **建议**     | 测 Host↔多 IG 链路、CIGI 收发、帧栅栏、Present 协调（可用 mock/假时钟） |

### 1. 时钟同步 — 单元 / 轻集成

- **偏移估计**：给定一组 Host/IG 时间戳样本，校验估算出的 offset / drift 是否在容差内。
- **漂移补偿**：模拟 IG 时钟相对 Host 每秒慢 N μs，验证校正后误差收敛。
- **乱序 / 丢包**：延迟、乱序、丢失同步包时，算法不发散、不跳变过大。
- **超时与降级**：长时间收不到 sync 时进入 fallback（本地时钟 / 冻结 / 告警），恢复后能重新锁定。
- **单调性**：校正后的“仿真时间”不回退（或回退策略符合设计）。

示例断言思路：`|t_ig_corrected - t_host| < threshold`；注入 50ms 延迟后仍满足；断连 2s 后状态变为 `Degraded`。

---

### 2. 状态同步（CIGI）— 单元为主 + 协议集成

- **编解码往返**：Entity / View / Component Control 等包 encode→decode 字段一致。
- **帧号 / 序号**：Host 发 frame N，IG 按序应用；乱序包丢弃或缓冲到正确帧。
- **幂等与滞后**：同一帧重复到达不重复应用；过期帧被拒绝。
- **状态机**：`Disconnected → Connected → Synced → Error` 在合法/非法序列下转换正确。
- **部分通道失败**：1 个 IG 超时，其余通道是否继续、Host 是否标记该通道 stale。
- **大数据 / 边界**：最大实体数、超长包、非法 opcode 的处理（拒绝而非崩溃）。

示例：构造一帧含 Entity Control + View Control 的 CIGI 消息，mock IG 应用后检查位姿/视锥与 Host 期望一致。

---

### 3. 软件显示同步（Render / Present 时机）— 单元 + 集成

这是最值得测、也最容易只靠“看起来齐”漏掉的部分。

**单元（调度逻辑，假时钟 / mock GPU）：**

- Host 发出 `BeginFrame(frameId)` 后，各通道只有在收到后才进入 render。
- 所有通道 `RenderComplete` 齐了，才允许 `Present`；任一通道超时则按策略跳过 / 整帧丢弃 / 超时 Present。
- 帧栅栏：通道 A 仍在 frame N 时，不能 Present frame N+1。
- 背压：某通道持续落后时，Host 是否限速、丢帧或扩大缓冲（符合设计）。

**集成（进程内多“假 IG”或单机多 viewport）：**

- 3 个 mock 通道按不同耗时完成 render，Present 调用顺序/时刻满足“齐套后再 present”或你们定义的 barrier。
- Host 暂停 / 单步一帧时，所有通道停在同一 `frameId`。
- 一通道故意慢 1 帧，验证不同步帧不会被一起 Present（或按设计打出 warning）。

示例时间线断言：

```text
Host: Frame 10 start
IG0/1/2: render done @ t=..
Host: barrier release
IG0/1/2: present called within Δt < present_skew_limit
且 present 的 frameId 均为 10
```

---

### 4. 建议优先落地的用例（MVP）

若资源有限，先做这 6 类，性价比最高：

1. CIGI 关键包编解码往返  
2. 帧序号乱序/过期丢弃  
3. 时钟 offset 估计在噪声下的误差上界  
4. Present barrier：未齐套不 Present  
5. 单通道超时的降级策略  
6. 多通道 mock 集成：同一 `frameId` 下状态一致后再 Present  

真机多 GPU 的“肉眼对齐 / 拍照比对”可作为发布前 checklist，不必一开始就全自动化。





### 结论

- **需要**单元测试和集成测试，尤其是时钟校正、CIGI 状态应用、Present 栅栏三类纯逻辑。  
- GPU 真实 Present 与跨机 PTP/网络抖动，自动化成本高，用少量集成 + 手工/脚本验收即可。  
- 测试重点不是“画面好不好看”，而是**帧一致性、时序约束、故障降级**是否可重复验证。
